## 2. 코드 개선 (`v2r/knowledge/keyword_fill_loop.py`)

- **(a) 출처별 예산 자동 조절**: 기존 `weighted_cap`(경쟁·자동완성·연관검색·파생 채택률 비례)을 **정리본**에도 적용(`guide_cap`). 확정률 낮은 출처는 다음 회차 상한이 자동으로 줄어든다(0.4배에서 2.5배).
- **(b) 2단계 확장**: 1단계 자동완성·연관검색 결과 상위 10개를 다시 자동완성·연관검색에 넣어 "확정 → 연관 → 그 연관의 연관"을 수집한다(`DEFAULT_EXPAND_DEPTH2_TOP_N=10`, 회차당 상한 `DEFAULT_EXPAND_DEPTH2_CAP=60`, 채택률로 조절).
- **(c) 흐름 제어**: `score_backlog_count()`(미채점 행 수)가 5,000 이상이면 그 회차는 수집을 건너뛴다(`DEFAULT_SCORE_BACKLOG_PAUSE=5000`). 실측: 재기동 직후 장으뜸이 적체 6,188건으로 즉시 이 규칙에 걸려 수집을 멈춤(로그 `logs/keyword-fill-장으뜸.log`).
- **(d) 재수집 방지**: `rejected_keywords`에 있는 후보는 키워드 도구 조회 결과에서 저장 전에 걸러낸다(기존엔 시드 선택 단계에서만 걸렀고, 조회로 돌아온 확정 무관 후보는 다시 저장되고 있었다).
- 200,000 상한(`DEFAULT_CAP`)은 그대로 유지.

## 3. 적용 및 1회차 실측

기존 채우기 프로세스 4개를 종료 후 `scripts/keyword-fill-worker.vbs <브랜드> 10000 b`(wscript, 숨김)로 재기동. 재기동 시점 확인 결과 요청한 4개 프로세스 외에 무관 브랜드("갱년기") 워커가 이미 떠 있었으나 이번 작업 범위 밖이라 손대지 않았다.

채점은 상주 워커(`score_worker`/`codex_worker`)가 비동기로 처리하므로(`AUTO_SCORE_IN_FILL_LOOP=False`), 재기동 직후 1회차의 `adoption_rate`는 아직 스코어링이 못 따라간 값이라 확정률과 직접 비교할 수 없다. 대신 수집량·흐름 제어 동작을 실측했다.
