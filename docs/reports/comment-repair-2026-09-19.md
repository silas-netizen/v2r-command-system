# 제휴 수정글 댓글 역할 복구 (2026-09-19)

2026-09-19에 만든 제휴 수정글 3건의 댓글2 스레드가 전부 **본문 작성자 한 계정**으로
잡혀 있었다(`docs/reference/live-comment-order.md` §4). 작성자가 혼자 묻고 스스로
제품명을 답하고 스스로 "222 저도 효과 봤어요"까지 다는 모양이었다.
세 건 모두 예약(`RESERVED`) 상태라 **지우고 같은 내용으로 다시 등록**해서 고쳤다.

계정은 앞 3글자만 남긴다. 시각은 모두 UTC(`Z`)다.

## 1. 방법

`v2r/engine/repair.py::repair_revision_comments`

1. `GET /naver_cafe_articles/article` 로 제목·`tag_list`·본문(`…source_detail.body`를
   `content_json`으로 **그대로**)·목적지(cafe_id·menu_id·말머리·작성계정·`start_at`·
   `target_view_count`·`write_options`)·`parent_source_id`·댓글 12건을 확보한다.
2. 댓글 본문은 라이브 배열 순서(= 읽는 순서)가 `DEFAULT_TREE`와 같으므로 자리끼리
   라벨(댓글1..5 / 대댓글N / 대대댓글2 / 대대대댓글2)에 그대로 붙인다.
3. `content/comments.py`로 **계정만** 다시 배정한다
   (`assign_comment_accounts(..., manuscript_type)` → `schedule(수정글 start_at)` →
   `resolve_conflicts` → `to_api_payload(members=catalog.cafe_accounts(cafe_id))`).
4. 원글 삭제(`article/delete` — 딸린 예약 댓글도 함께 취소된다, api-spec §9) 후
   같은 제목·태그·본문·목적지·`parent_source_id`로 재등록한다.
5. 재등록한 글을 다시 `GET`해서 `verify_article`(제목·태그·게시판·본문 문단·
   이미지 수·예약시각·댓글 수·**읽는 순서**) + 노드별 **작성 계정·`reply_member`**
   까지 검사한다.

안전장치: 예약 상태가 아니거나, 수정글이 아니거나, 댓글 예약 시각이 이미 지났거나,
댓글이 12개가 아니면 아무것도 하지 않고 이유만 돌려준다. 기본은 모의 실행이고
실제 실행에는 명령에 `실제 발행`이 있어야 한다.

명령: `댓글 … 다시 세팅 / 재설정 / 복구` + 글의 26자리 source_id
(작업 `repair_comments`, 파서 `댓글.*(복구|재설정|다시)`).

## 5. 남은 것

- 팥순이#3·우아덤#2는 `tag_list`가 **빈 배열**이다. 복구는 원본을 그대로
  보존하는 것이 원칙이라 손대지 않았다. 원인(발행 당시 키워드→태그 누락)은
  이 복구와 별개 건이다.
- 예약 댓글만 따로 지우는 엔드포인트(`comment/delete` 계열)는 여전히 미검증이다.
  검증되면 글을 지우지 않고 댓글만 갈아끼울 수 있어 `parent`/`child` 재연결과
  새 source_id 발급이 필요 없어진다.
