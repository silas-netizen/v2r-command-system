# 노출 확인 러너 "동시 정지" 원인 조사 — 2026-09-26 2차

목표: 이전 보고서(`exposure-speed-2026-09-26.md` 4절)가 남긴 "작업자 전원이
거의 동시에 2에서 3분씩 멈추는 패턴"을 계측으로 확정하고 고친다.

## 1. 계측 추가

- `v2r/store/exposure_queue_store.py`: `claim_batch`·`upsert_candidates`의
  `BEGIN IMMEDIATE` 락 대기 시간을 재서, 0.5초 넘으면 로그(`타이밍
  claim_batch 락대기=...`, `타이밍 upsert_candidates 락대기=...`).
- `v2r/knowledge/keyword_exposure.py`: `_article_cache_load`/`_article_cache_save`
  (공유 캐시 `exposure_article_cache.json`) 읽기·쓰기 시간을 재서, 0.5초
  넘으면 로그.

두 계측 모두 로그량을 줄이려고 임계값을 넘는 건만 남기게 했다(요청한
"과하면 debug로" 조건을 만족해 info로 뒀다 — 게이트가 있어 정상 상태에서는
거의 안 찍힘).

## 2. 1차 실측(10:46에서 11:05, 작업자 6개, 계측 켠 뒤)

- DB 락 대기: 작업자 6개 × 2,400에서 3,500여 건의 `claim_batch`/
  `upsert_candidates` 호출 중 **0.5초 넘는 락 대기 0건**. 파일 캐시 읽기·쓰기도
  **0.5초 넘는 건 0건**. → **DB 경합·공유 파일 잠금은 배제**(계측으로 확정).
- 그런데도 작업자 0에서 5 전원의 로그가 **10:57:35부터 11:04:45까지(약 7분)**
  거의 동시에 멈췄다 — 이 구간에 Naver 요청이 전혀 없고, 구글시트 CSV
  읽기·Apps Script POST(시트 반영)만 몇 건 있다가 뚝 끊겼다.
- `logs/exposure-runner-watchdog.log`(예약 워치독, 5분 간격 `is_alive`
  검사)를 대조하니 **11:04:32에 "러너 작업자 없음 - 작업자 6개로 재기동"**이
  찍혀 있었다 — `is_alive`는 공유 상태 파일(`data/exposure_runner_state.json`)
  하나의 `updated_at`이 180초 안에 갱신됐는지만 본다(작업자 개별이 아니라
  전체 판정). 즉 **작업자 6개 전원이 실제로 180초 넘게 상태 파일을 갱신하지
  못했다** — 로그가 조용해진 게 착시가 아니라 실제로 전원이 멈췄다는
  뜻이다.
- `data/v2r.sqlite`의 `exposure_queue.enqueued_at`(브랜드별 큐 갱신 시각)을
  대조하니, 정지 구간 경계(10:57 직전·11:00 직후·11:07)에 여러 브랜드의 큐
  갱신이 몰려 있었다 — 그 중 한 브랜드(19,068행, 가장 큰 시트)는 이
  구간에서 갱신이 안 됐다. `_do_refresh_queue`(우선순위 재계산, 수천에서
  19,068개 항목을 파이썬 for문으로 순회)는 코디네이터 지시대로 이미
  백그라운드 스레드에서 도는데(2026-09-24 6차), Python은 GIL 하나를
  공유하므로 이 CPU 위주 루프가 도는 동안 **그 프로세스의 메인 스레드도
  같이 묶인다** — 그리고 재기동 직후에는 모든 작업자 프로세스의 TTL
  시계가 같은 시각에서 출발하므로, 브랜드별 큐 갱신(기본 600초 TTL)이
  같은 몇 분 사이에 몰릴 수 있다는 게 이번 실측(재기동 직후 발생)의
  정황이었다.

## 3. 적용한 조치

`v2r/knowledge/exposure_priority.py`의 `maybe_refresh_queue` — TTL 판정
자체(`last_refreshed_at` 비교)는 시험이 기대하는 그대로 두고, **백그라운드
갱신 스레드의 시작 시각만** 브랜드 이름의 안정적 해시로 0에서 19초
사이로 미뤄, 같은 순간에 만료된 여러 브랜드의 무거운 재계산이 겹치지
않게 흩뿌렸다(락은 이미 잡아 둔 상태라 다른 프로세스가 같은 브랜드를
다시 시도하진 않는다). 시험 148건(`tests/test_exposure_runner.py`,
`tests/test_keyword_exposure.py`, `tests/test_keyword_exposure_cycle.py`)
모두 통과.

## 4. 2차 실측(11:31에서 12:02, 작업자 6개, 조치 적용 뒤) — **효과 없음**

- 처리량: 30분 동안 100건(`keyword_exposure.checked_at` 기준) → 시간당 환산
  **약 200건** — 조치 전 기준(403에서 415건/시)보다 오히려 낮았다.
- 워치독 로그: 같은 30분 창 안에서도 **11:49:23·11:59:21 두 번 더
  "작업자 없음 - 재기동"**이 찍혔다 — 조치 후에도 전원 동시 정지가
  계속됐다.
- 작업자 0의 로그를 전 구간(11:05에서 12:02) 훑어보니 90초 넘는 간격이
  11건, 그 중 300초를 넘는 것도 2건(569초, 385초) — **정지가 특정 TTL
  경계 한 번이 아니라 산발적으로, 그것도 더 자주 일어났다.** 정지 직전
  마지막 로그가 매번 다르다(구글시트 POST, HTTP 요청, 타이밍 로그 등
  일정하지 않음) — 확인(confirm) 단계의 `total=` 값 자체는 이 구간에
  20초를 넘는 건이 1건뿐이라, "느린 확인이 쌓여서"도 아니었다.
- 결론: **큐 갱신 CPU 작업의 동시 발생은 원인의 일부였을 수 있지만
  전부가 아니다.** 지터를 줘도 동시 정지가 없어지지 않았고 오히려 이번
  창의 처리량은 더 나빴다(표본 30분이라 변동일 가능성은 있다).

## 5. 배제한 것 / 남은 후보

배제(계측으로 확정): sqlite 락 대기, 공유 JSON 캐시(판정 캐시) 파일
잠금 대기, 시트 반영 배치(별도 스레드, DB 미사용 — 코드 확인 완료),
confirm 단계 개별 지연(1건 제외 전부 20초 미만).

남은 후보(이번 회차 시간 안에 확정 못함):
1. 작업자 프로세스마다 Playwright(Chromium)를 상주시키므로, 6개
   프로세스의 브라우저 프로세스들이 CPU·디스크 I/O(로그 파일, 프로필
   캐시)를 놓고 경합해 OS 수준에서 전원이 같이 느려질 가능성 — 코드
   계측(Python 로그)으로는 못 잡는다. Windows 성능 카운터나
   Process Monitor 같은 OS 도구로 다시 봐야 한다.
2. Naver 쪽에서 같은 IP(이 PC)로 오는 요청을 일시적으로 늦게 응답하되
   차단 징후(캡차·unknown 급증)는 안 보이는 형태로 조절할 가능성 —
   confirm/scroll의 `타이밍` 로그가 "느리게 끝남"이 아니라 "그 줄 자체가
   안 찍힘"으로 나타나므로, 어느 함수 안에서 멈췄는지 더 잘게 쪼갠
   계측(예: `page.goto` 호출 직전·직후에도 타임스탬프)이 있어야 구분된다.
