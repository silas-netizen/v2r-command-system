# 노출 확인 속도 개선 — 러너 구현 + 실측 (2026-09-24)

## 0. 요약

상주 브라우저 작업자 + 스크롤 조기 종료 + 우선순위 큐(`docs/reports/exposure-speed-plan-2026-09-23.md`
설계)를 구현하고 작업자 2·3·4·5·6개로, 우선순위 큐 구조를 여섯 차례에
걸쳐 개선하며 총 열한 번 실측했다(마지막 라운드, 6-10절). 판정 규칙
(`v2r/knowledge/keyword_exposure.py`)은 그대로 두고 호출만 한다. 과정에서
진짜 버그 8개를 실측 중에 발견·수정했다(그중 하나는 "고치고 실측했더니
더 나빠져서 되돌린" 사례 — 6-4절) — 아래 1절에 시간 순으로 정리했다.

**최종 결론(마지막 라운드, 08:05 기준, 작업자 6개·간격 3–5초·큐 갱신
백그라운드화 반영 후) — "정식 가동 확정"은 아니고 "지금 상태로 운영
지속"을 권고한다(6-10절 상세).** 목표는 고유 키워드 기준 시간당 700건
이상 + 같은 창 안 중복 3% 이하 **둘 다** 였는데, 마지막 라운드는 **중복률
(1.4%)은 처음으로 목표를 통과**했지만 처리량(고유 시간당 약 552건)은
여전히 못 미친다. 원본(중복 포함) 처리량은 시간당 최고 660건까지 올라
기존 77건/시 대비 **약 8.6배**를 확인했다.

큐 조회는 작업자별 독립 캐시(프로세스 메모리) → DB 공유 큐 → 갱신
백그라운드화를 거치며 **9.9초 → 3.2초 → 2초 → 0.07초**로 사실상
완전히 해소됐고, 중복률도 함께 9.4% → 19.4% → 3.5% → **1.4%**로
내려왔다(초반엔 속도와 중복률이 트레이드오프로 보였지만 — 6-4~6-7절 —
근본 원인인 프로세스별 캐시를 없애자 둘 다 좋아졌다). 마지막 조정
(작업자 5→6, 간격 6–10초→3–5초)에서도 차단 징후는 끝까지 0건이었다 —
되돌릴 필요 없이 이 설정을 새 기본값으로 유지한다. 남은 병목은 이제
큐가 아니라 검사 1건 자체(평균 9.9초)와 작업자 수 대비 처리량 정체로
옮겨갔다(6-10절). 과정에서 브랜드를 고정해 캐시 재사용을 늘리려던 시도
(6-4절)가 프로세스별 독립 캐시 때문에 중복 67%까지 치솟아 되돌린 사례도
있었다.
