# 통검 1등 "카페 글" 형식 참고 — 구현·실측 보고 (2026-09-23 갱신, 15:52 작성)

> **정정 이력**: 처음엔 "카페>블로그>포스트>지식iN 순으로 첫 일반 글"을 1등 글로 잡았다. 사용자가 "참고할 1위 글은 **카페 글만**"으로 정정해, 아래는 카페 전용으로 다시 만든 결과다. 이전 버전(블로그 포함) 데이터는 폐기했다.

## 무엇을 만들었나

`v2r/content/top_reference.py`. 흐름:

1. `resolve_search_query`(자동완성 정규화) → `fetch_integrated_search_dom`(헤드리스, 끝까지 스크롤)로 네이버 통합검색 최종 DOM을 받는다.
2. 광고·쇼핑·뉴스를 빼고 **카페 글(`cafe.naver.com`)만** 대상으로, 화면 등장 순서상 **첫 번째 카페 글**을 1위로 잡는다. `config/bulk.yaml`의 `top_reference.sources`(기본 `["cafe"]`)로 소스를 넓힐 수 있게 만들었다 — `_pick_top_link(dom_html, sources=[...])`.
3. 카페 글이 통검 첫 페이지에 없으면 `{"error": "카페 글 없음"}`으로 캐시한다(성공 캐시와 같은 파일 자리, TTL만 1일).
4. 고른 카페 글을 `m.cafe.naver.com` 주소로 다시 열어(`#cafe_main` iframe 안 본문) 텍스트를 뽑고, 제목 유형·글자수·단락 수·도입 방식·전개 순서·마무리 유형·사진 수·목록/소제목 사용 여부를 계산한다.
5. `format_brief`가 300~400자 한국어 요약으로 압축한다. 문장은 한 줄도 인용하지 않고, 마지막 줄에 항상 `※ 형식만 참고. 문장·표현·사례는 절대 베끼지 말고 우리 브랜드 가이드 논리로 새로 쓴다.`를 붙인다.
6. `reference_for(rt, brand, keyword)`가 검색량 조건(브랜드 pool 상위 50% 또는 검색량 100 이상)을 만족할 때만 brief를 돌려준다. 캐시는 `data/top_reference/<키워드>.json`(TTL 7일, 실패는 1일).
7. brief는 `brand_writer.build_body_prompt`/`build_combined_prompt`의 **user 프롬프트에만** `【참고 형식(통검 1등 글)】` 블록으로 붙는다 — 브랜드 공용 system(프롬프트 캐시 대상)은 손대지 않는다.
8. `bulk_generate.generate_for_brand`가 각 키워드마다 `reference_for`를 부르고, `stats["reference_used"]`/`stats["reference_url"]`을 원고 JSON에 남긴다.

### 캐시 스키마 버전(구버전 무효화)

카페 전용으로 바꾸면서 캐시 내용 자체가 달라져(`serp`·`rank_in_source` 등 추가), `_save_cache`가 항상 `"version": 2`를 적고 `_load_cache`는 버전이 다르면(또는 없으면) 무효로 본다. **옛 캐시(블로그 포함 시절) 15개는 모두 삭제**하고 카페 전용으로 다시 수집했다.

### 순위·순번·교차검증·스크린샷

- `extract_serp(dom_html, max_n)`이 화면 등장 순서대로 결과를 훑어 `serp: [{rank, section, source, title, url, is_ad}]`(저장은 상위 15개)를 만든다. 섹션은 도메인 기반 어림이다(한계는 아래 절 참고).
- 우리가 고른 카페 글의 **세 가지 순번**을 계산해 저장한다:
  - `rank_overall`: 광고 포함 전체 화면 순번(상위 200개까지 넉넉히 훑어서 계산)
  - `rank_organic`: 광고·쇼핑을 뺀 순번
  - `rank_in_source`: **카페 글끼리만** 셌을 때 몇 번째인가 (2026-09-23 정정 지시로 추가)
- 교차검증: 같은 검색어를 requests 기반(`fetch_integrated_search_html`, 비로그인·스크롤 없음)으로 한 번 더 조회해 **첫 카페 글**을 뽑고, Playwright(로그인 프로필) 결과와 URL을 비교해 `crosscheck_match`를 남긴다.
- 스크린샷 1건: `data/top_reference/더마팩토리.png`(창 없이 헤드리스 캡처, 1440×1400).

## 실패 사례와 대처

- **정규화 미스매치로 순번 미확인**: 15개 중 1개(리쥬란)에서 rank_overall/rank_organic/rank_in_source를 못 찾았다. brief 자체는 정상 생성됐다. 원인은 알려진 결함(URL 캡처 정규식의 미세한 차이)으로 문서화만 하고 이번 작업 범위에서는 고치지 않았다.
- **파워링크 광고 중복 집계**: 광고 한 칸에 썸네일/제목/설명 등 여러 클릭 영역이 있어 URL이 조금씩 다르다. 리다이렉트 토큰 앞 16자로 묶어 광고 1칸을 1건으로 집계한다(이전 보고서에서 고친 내용, 카페 전용으로 바꾼 뒤에도 그대로 유효).
- **`load_recent_openings` 예외**: 원고 생성 실측 중 `warehouse/manuscripts/generated/_top_reference_trial/`에 저장했던 시험용 요약 JSON(`list` 꼴)을 그 함수가 `dict`로 착각해 죽는 실제 버그를 발견했다. `v2r/content/brand_writer.py`의 `load_recent_openings`에 "JSON이 dict가 아니면 건너뛴다" 방어 코드를 추가해 고쳤다(운영 중 원고 생성 트리에 어떤 형태의 파일이 섞여도 죽지 않게).
- **카페 글 없음 사례**: 15개 키워드 전부 카페 글을 찾아 이번 실측에서는 발생하지 않았다. `{"error": "카페 글 없음"}` 캐시·빈 brief 경로는 유닛테스트로 확인했다.

## 한계 (정직하게 적어 둔다)

- SERP 섹션 이름은 도메인 기반 어림이다. 네이버가 화면에 실제로 붙이는 "VIEW"·"인플루언서" 헤딩까지 읽으려면 섹션 컨테이너의 CSS 구조를 구조적으로 파싱해야 하는데, 이번 구현은 정규식 기반이라 거기까지는 안 갔다. 등장 순서(rank)는 정확하다.
- URL 정규화 미스매치로 순번을 못 찾는 경우가 15건 중 1건 있었다.
- "카페 중 몇 번째"만 볼 뿐, 그 카페 글이 실제로 좋은 글인지는 안 본다(광고성 카페 홍보 글일 가능성도 있다 — 이번 5건은 실제로 열어 본문을 읽어 확인했고 전부 사용자 상담/후기 글이었다).
