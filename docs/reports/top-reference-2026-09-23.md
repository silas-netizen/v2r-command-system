# 통검 1등 글 "형식" 참고 — 구현·실측 보고 (2026-09-23 15:07 작성)

## 무엇을 만들었나

새 모듈 `v2r/content/top_reference.py`. 흐름:

1. `resolve_search_query`(자동완성 정규화) → `fetch_integrated_search_dom`(헤드리스, 끝까지 스크롤)로 네이버 통합검색 최종 DOM을 받는다.
2. 광고/쇼핑/뉴스를 뺀 **첫 일반 글**(카페 > 블로그 > 포스트 > 지식iN 순으로 먼저 등장하는 것)을 고른다.
3. 그 글을 모바일 주소로 다시 열어(카페는 `#cafe_main` iframe) 본문 텍스트만 뽑고, 제목 유형·글자수·단락 수·도입 방식·전개 순서(단락별 첫 문장 3~5개)·마무리 유형·사진 수·목록/소제목 사용 여부를 계산한다.
4. `format_brief`가 이걸 300~400자 한국어 요약(brief)으로 압축한다. **문장은 한 줄도 인용하지 않고**, 마지막 줄에 항상 `※ 형식만 참고. 문장·표현·사례는 절대 베끼지 말고 우리 브랜드 가이드 논리로 새로 쓴다.`를 붙인다.
5. `reference_for(rt, brand, keyword)`가 검색량 조건(브랜드 pool 상위 50% 또는 검색량 100 이상, `config/bulk.yaml`의 `top_reference.top_pct`/`min_volume`)을 만족할 때만 brief를 돌려준다. 캐시는 `data/top_reference/<키워드>.json`(TTL 7일, 실패는 1일).
6. brief는 `brand_writer.build_body_prompt`/`build_combined_prompt`의 **user 프롬프트에만** `【참고 형식(통검 1등 글)】` 블록으로 붙는다 — 브랜드 공용 system(프롬프트 캐시 대상)은 손대지 않는다.
7. `v2r/content/bulk_generate.py`의 `generate_for_brand`가 각 키워드마다 `reference_for`를 부르고(실패해도 무시), `stats["reference_used"]`/`stats["reference_url"]`을 결과 JSON에 남긴다.
8. `config/bulk.yaml`에 `top_reference: {enabled: true, ttl_days: 7, top_pct: 50, min_volume: 100}` 추가.

CLI 점검용: `python -m v2r.content.top_reference <키워드> [--brand 브랜드]`.

### 순위·교차검증·스크린샷 (추가 지시)

- `extract_serp(dom_html, max_n)`이 통검 최종 DOM을 화면 등장 순서대로 훑어 `serp: [{rank, section, source, title, url, is_ad}]`를 만든다. 섹션은 **도메인으로 어림**한다(파워링크/광고·쇼핑·뉴스·카페·블로그·포스트·지식iN) — 네이버가 실제로 붙이는 "VIEW"·"인플루언서" 같은 화면 제목까지는 순수 정규식 파싱으로 읽지 못한다(한계, 아래 "한계" 절 참고). 화면에 뜨는 **순서 자체**는 정확하다.
- 우리가 고른 글의 `rank_overall`(광고 포함 전체 순번, 상위 200개까지 훑어서 계산)과 `rank_organic`(광고·쇼핑을 뺀 순번)을 `data/top_reference/<키워드>.json`에 저장한다. 저장하는 `serp` 배열 자체는 지시대로 상위 15개만 남긴다.
- 교차검증: 같은 검색어를 **requests 기반**(`fetch_integrated_search_html`, 비로그인·스크롤 없음)으로 한 번 더 조회해 첫 일반 글을 뽑고, Playwright(로그인 프로필·끝까지 스크롤) 결과와 URL을 비교해 `crosscheck_match`를 남긴다.
- 스크린샷 1건: `data/top_reference/더마팩토리.png`(창 없이 헤드리스 캡처, 1440×1400).

| 브랜드/키워드 | 시도 횟수(기존→참고) | 출력 토큰(기존→참고) | 신규 캐시 생성 토큰(기존→참고) | brief 길이(자) |
|---|---|---|---|---:|
| 우아덤/더마팩토리 | 2 → 3 | 11,520 → 17,554 (+6,034) | 1,791 → 1,945 (+154) | 141 |
| 팥순이/스포츠 | 3 → 3 | 15,706 → 11,644 (−4,062) | 2,913 → 2,885 (−28) | 141 |
| 장으뜸/병원 | 2 → 2 | 7,830 → 9,630 (+1,800) | 1,723 → 1,908 (+185) | 136 |
| 코숨핏/미세먼지 | 3 → 3 | 9,289 → 8,672 (−617) | 2,560 → 3,115 (+555) | 141 |
| 뉴더미스/유산균 | 3 → 3 | 9,006 → 10,145 (+1,139) | 20,033 → 1,919 (−18,114)* | 139 |

\* 유산균 "기존" 쪽 캐시 생성 토큰이 유독 큰 건 이 실행에서 그 브랜드 system 프롬프트가 캐시에 처음 올라간 시점(콜드 스타트)이라서다 — brief와 무관.

**결론**: brief 자체는 136~141자(한국어라 대략 90~110토큰)로 짧다. 하지만 실제 입출력 토큰 변화는 **±6천 토큰까지 들쭉날쭉**했다 — 이는 brief 때문이 아니라 본문 검증 재시도 횟수(2~3회, 위반이 남으면 다시 쓰게 하는 기존 로직)가 매번 달라서다. brief가 붙는다고 재시도 횟수가 늘거나 준 것도 아니다(스포츠·미세먼지는 재시도 그대로, 병원은 그대로, 더마팩토리만 2→3). 5건으로는 "brief가 토큰을 일정하게 늘린다"고 말하기 어렵다 — 순수 추가분은 매 호출 user 프롬프트에 ~100토큰 얹히는 정도로 보면 된다.

## 실패 사례와 대처

- **1등 글 순번 계산 실패 2건**(미녹시딜·비만도계산기): 위 표에 "미확인"으로 남기고 원인(URL 정규화 불일치 추정)을 적었다. brief 생성 자체는 정상 동작했다(전체 15건 성공).
- **초기 SERP 오탐**: 처음 구현에서 상단 메뉴("내 블로그", 카페/뉴스/지식iN 바로가기)를 결과로 잘못 집계했다. 도메인 루트 경로(`/`)는 실제 결과가 아니라고 보고 제외하도록 고쳐서 해결했다(위 "더마팩토리" SERP 예시가 고친 뒤 결과).
- **파워링크 광고 중복 집계**: 광고 한 칸에 썸네일/제목/설명 등 여러 클릭 영역이 있어 URL이 조금씩 달라 같은 광고가 4~8번 잡혔다. 리다이렉트 토큰 앞 16자로 묶어 광고 1칸을 1건으로 집계하도록 고쳤다.
- **제목 추출 정확도**: 정규식만으로 DOM을 훑다 보니 광고 영역 제목은 HTML 속성 조각이 섞여 나온다(위 SERP 예시에 명시). 카페·블로그 등 일반 글 제목은 글 자체를 열어 `<title>` 태그로 다시 뽑아 정상적으로 나온다(보고서의 brief·비교표 제목은 전부 이 방식).
- **캐시 실패 처리**: 코드상 수집 실패는 `{"error": ...}`로 1일만 캐시해 반복 실패를 막는다 — 이번 실측에서는 실패 사례가 없어 이 경로는 유닛테스트로만 확인했다.

## 한계 (정직하게 적어 둔다)

- SERP 섹션 이름은 도메인 기반 어림이다. 네이버가 화면에 실제로 붙이는 "VIEW"·"인플루언서" 헤딩까지 읽으려면 섹션 컨테이너의 CSS 구조를 구조적으로 파싱해야 하는데, 이번 구현은 정규식 기반이라 거기까지는 안 갔다. 등장 순서(rank)는 정확하다.
- URL 정규화 미스매치로 순번을 못 찾는 경우가 15건 중 2건 있었다(위 실패 사례).
- 1등 글 판정은 "광고·쇼핑·뉴스를 뺀 첫 일반 글"만 본다 — 실제 사용자가 가장 많이 클릭하는 글(예: VIEW 탭 상단)과 다를 수 있다.
