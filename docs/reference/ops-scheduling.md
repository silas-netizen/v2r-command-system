# 예약과 감시 (운영 기준 문서)

배경: **2026-09-20 09:00 장애.** 윈도우 작업 스케줄러가 `scripts/enqueue-0900.cmd`
를 불렀지만 cmd가 한글 인자를 깨뜨려 `자사 카페 일상 글 카페별 100건 실제 발행 댓글 랜덤`
이 큐에 들어가지 않았다. 09:29까지 아무도 몰랐다.

사용자 규칙(최우선): **예약 기능이 틀어지면 즉시 감지·복구. 재발 금지.**

---

## 1. 누가 1순위인가

| 순위 | 수단 | 하는 일 |
|---|---|---|
| **1순위** | **실행기 내장 예약** (`v2r/engine/schedule.py`, `serve()` 안에서 돈다) | 모든 예약을 여기서 쏜다. cmd도 코드페이지도 끼지 않는다 |
| 2순위(백업) | 윈도우 작업 `V2R-Reconcile`, GPT 점검 작업 | 실행기가 아예 죽었을 때를 위한 안전망. 지우지 않는다 |
| 안전망 | 윈도우 작업 `V2R-Health` (`scripts/health-check.cmd`, 5분마다) | 심장박동이 3분 넘게 없으면 `V2R-Serve` 를 다시 켠다 |

실행기는 `scripts/serve.cmd` 로 24시간 돌고, 죽으면 30초 뒤 스스로 다시 켜진다.

### 관련 파일

| 파일 | 뜻 |
|---|---|
| `config/schedule.yaml` | 예약표(이름·시각·요일·명령) |
| `config/monitor.yaml` | 감시 설정(모델 진단 on/off, 하루 상한, 요약 시각, 캐시) |
| `v2r/engine/schedule.py` | 예약 발사 + 예약 감시견 + 심장박동 |
| `v2r/engine/monitor.py` | **모든 작업** 감시견 (Tier 0/1/2) |
| `v2r/engine/recovery_rules.py` | 오류 문구 → 복구 규칙 표 (토큰 0) |
| `data/schedule_state.json` | 예약별 마지막 발사일 + 확인 대기 목록 |
| `data/monitor_state.json` | 작업별 알림 여부·재시도 횟수·하루 집계 |
| `data/serve_heartbeat.json` | 실행기 심장박동(매 틱 기록) |

## 2. 예약 흐름

`serve()` 는 폴링 1회마다 `worker.watch_tick(rt)` 를 부른다.

1. **예약 감시견** — 조금 전에 쏜 예약이 정말 큐에서 움직였는지 본다(5분).
2. **발사** — `due_entries(now, last_fired)` 가 고른 예약을 `worker.handle_text` 로 접수.
3. **작업 감시견** — 큐의 모든 작업을 점검(§3).
4. **심장박동** — `data/serve_heartbeat.json` 에 시각을 적는다.

규칙

- **두 번 쏘지 않는다** — `last_fired[이름] == 오늘` 이면 건너뛴다. 상태가 파일에 있으므로
  실행기를 껐다 켜도 같다.
- **놓친 예약은 따라잡는다** — 실행기가 꺼져 있었으면 켜지자마자 쏜다.
  기본 창은 **그날 23:59까지**. 좁히려면 `catch_up_minutes` 를 적는다.
- **중지에 막히지 않는다** — 예약을 쏘기 직전에 오래된 `data/STOP` 플래그를 지운다.

### 예약 감시견 (발사 후 5분)

| 시점 | 행동 |
|---|---|
| 5분 안에 작업이 `running`/`done` | 조용히 끝 |
| 5분이 지나도 `queued`거나 작업이 없음 | `예약 실패: <이름> — 자동 재시도` 알림 + **한 번** 재발사 |
| 그 뒤로도 5분 더 움직이지 않음 | 이유를 붙여 알림 + `error` 이벤트 기록 (사람 차례) |

## 3. 모든 작업 감시

사용자 규칙: **"모든 명령에 감시 에이전트 붙여."** 예약만이 아니라 큐에 들어온
모든 작업을 `v2r/engine/monitor.py` 가 매 틱 지켜본다.

| 상태 | 기준 | 자동 복구 |
|---|---|---|
| `queued` → 시작 안 함 | 5분 | `작업 N 시작 지연` 알림 + STOP 플래그 해제 + 만료된 실행기 리스 반납 |
| 그래도 시작 안 함 | 10분 | 이유(리스를 누가 잡고 있는지 등)를 붙여 다시 알림 |
| `running` 인데 기척 없음 | 15분 | `작업 N 정체 15분` 알림 |
| `running` 인데 30분 멈춤 + 리스 만료 | 30분 | 실패로 정리 → **같은 명령을 한 번** 다시 등록 |
| `failed` | 즉시 | 한 번만 알림 + 규칙에 따라 재시도/토큰 갱신/사람 |

"기척"은 `jobs.updated_at` 또는 그 작업의 마지막 이벤트다. 발행은 글 사이에 2~3분씩
쉬고 요청 제한에 걸리면 더 오래 기다리므로, `_sleep_with_beat` 와 `_wait_for_rate_limit`
가 **10분마다 진행 이벤트**를 남긴다(`PROGRESS_EVENT_S`). 그래서 정상 대기를 정체로
오해하지 않는다.

같은 알림을 되풀이하지 않도록 알림 여부와 재시도 횟수는 `data/monitor_state.json`
에 남는다(재시작해도 유지).

## 4. 비용 계단 (토큰을 태우지 않는다)

사용자 규칙: **감시는 기본적으로 AI 토큰을 쓰지 않는다.**

### Tier 0 — 기본, 토큰 0

순수 코드 점검만 한다. SQLite의 `jobs`·`events`, 심장박동 파일, 실행기 리스,
STOP 플래그, 세션 만료(`AuthSession.report()`). 복구도 규칙 기반이다:
STOP 해제, 만료 리스 반납, 한 번 재등록, 토큰 갱신, 실행기 재시작 안내.

오류 문구는 `v2r/engine/recovery_rules.py` 표로 맞힌다.

| 규칙 | 조치 | 뜻 |
|---|---|---|
| `rate_limited` | wait | 서버가 잠시 막음. 실행기가 기다린다 |
| `login_budget` | human | 하루 20회 로그인 한도 |
| `token_expired` | refresh | 토큰을 새로 받는다 |
| `network` | retry | 잠깐 끊김. 한 번 다시 |
| `catalog_mismatch` | human | 카페·게시판 이름이 사이트와 다름 |
| `photo_shortage` | human | 쓸 사진 부족 |
| `emoji` | human | 이모지 때문에 막힘 |
| `duplicate` | wait | 이미 올린 글(정상) |
| `lease_lost` | retry | 다른 실행기가 가져감 |

틱은 가볍게 유지한다(목표 50ms 미만). 같은 조회는 `cache_seconds`(기본 30초) 동안
다시 하지 않는다.

### Tier 1 — 선택, 상한 있음

**표에 없는 오류 문구일 때만** Haiku를 부른다.

- 같은 **오류 지문**(숫자를 지운 문구의 해시)당 **하루 한 번**.
- 하루 상한 `config/monitor.yaml: llm_diagnosis.daily_cap` (기본 20회).
- 하는 일은 딱 하나 — 기존 규칙 이름 중 하나로 **분류**하고 한국어 한 줄 설명을 준다.
- **절대 반복 호출하지 않는다.** 실패하면 그냥 Tier 2로 간다.
- 사용량은 `data/monitor_state.json` 의 그날 칸(`llm_calls`, `llm_tokens`)에 쌓이고
  텔레그램 `감시 상태` 에 그대로 보인다.

끄려면 `config/monitor.yaml` 에서 `llm_diagnosis.enabled: false`.

### Tier 2 — 사람

텔레그램 알림에 **규칙 이름 / 시도한 조치 / 그대로 복사해 보낼 재개 명령**을 넣는다.

```
작업 12 실패: 카페를 찾을 수 없습니다: 없는카페
판정: catalog_mismatch / 조치 human (Tier 0)
설명: 카페·게시판 이름이 사이트와 다릅니다. 카탈로그를 다시 읽어야 합니다.
다시 하려면 이렇게 보내세요: 카페 목록
```

## 5. 하루 요약 (08:35)

매일 `daily_summary_at`(기본 08:35)이 지나고 첫 틱에서 한 줄을 보낸다.

```
[감시 요약 2026-09-21] 작업 14건 (완료 12 / 실패 2), 자동 복구 1건, 알림 3건, 모델 진단 0회 (토큰 0)
```

모델을 한 번도 안 썼으면 `0회 (토큰 0)` 이다. 그게 정상이다.

## 6. 미처리 목록 + 현황판 하루 5번

`config/schedule.yaml` 의 `pending-1`~`pending-5` (08:40 · 11:00 · 14:00 · 17:00 · 21:00)
가 `미처리 알림` 명령을 돌린다. 이 작업(`pending_report`)은 텔레그램에 **파일 2개**를 보낸다.

1. `docs/reports/pending.md` — 캡션 `미처리 목록 <날짜 시각>`
2. `data/dashboard.html` — 새로 그린 뒤 캡션 `운영 현황판 <날짜 시각>`
   (claude.ai 쪽 현황판 사본은 실행기가 갱신할 수 없어서 파일로 보낸다)

텔레그램 Bot API `sendDocument`(multipart)를 쓴다 — `TelegramChannel.send_document` /
`broadcast_document`, 채널 공통 진입점은 `channels.notify_document_all`.

## 7. 건강 점검 (실행기가 죽었을 때)

```
python -m v2r health
```

심장박동 나이, 예약 목록(다음/마지막 실행), 세션 상태를 한 번에 보여 준다.

`scripts/health-check.cmd` 는 이 보고를 `logs/health.log` 에 남기고,
심장박동이 **3분**보다 오래됐으면 `schtasks /run /tn V2R-Serve` 로 실행기를 다시 켠다.

5분마다 도는 윈도우 작업으로 등록(관리자 명령 프롬프트, 한 번만):

```
schtasks /create /tn "V2R-Health" /tr "\"D:\v2r 자동화\v2r-command-system\scripts\health-check.cmd\"" /sc minute /mo 5 /f
```

## 8. 장애 시 자동 복구 흐름 (한눈에)

```
09:00  예약 발사 ────► 큐 등록 ────► 실행 ────► 완료
         │                │            │
         │ 5분 안 움직임   │ 5분 대기    │ 15분 기척 없음
         ▼                ▼            ▼
   "예약 실패 — 자동 재시도"   "시작 지연"    "정체 15분"
   (1회 재발사)          + STOP 해제    30분 + 리스 만료
                        + 리스 반납     → 실패 정리 + 1회 재등록
         │                │            │
         └────────── 그래도 안 되면 ─────┘
                          ▼
              Tier 2: 사람에게 알림
        (규칙 이름 + 시도한 조치 + 재개 명령)
```

실행기 자체가 죽으면 → 심장박동이 멈춤 → `V2R-Health`(5분) 가 `V2R-Serve` 재시작
→ 켜지자마자 그날 놓친 예약을 따라잡는다.
