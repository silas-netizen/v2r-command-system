# 예약과 감시 (운영 기준 문서)

배경: **2026-09-20 09:00 장애.** 윈도우 작업 스케줄러가 `scripts/enqueue-0900.cmd`
를 불렀지만 cmd가 한글 인자를 깨뜨려 `자사 카페 일상 글 카페별 100건 실제 발행 댓글 랜덤`
이 큐에 들어가지 않았다. 09:29까지 아무도 몰랐다.

사용자 규칙(최우선): **예약 기능이 틀어지면 즉시 감지·복구. 재발 금지.**

## 1. 누가 1순위인가

| 순위 | 수단 | 하는 일 |
|---|---|---|
| **1순위** | **실행기 내장 예약** (`v2r/engine/schedule.py`, **사이드카 스레드**에서 돈다 — §3-3) | 모든 예약을 여기서 쏜다. cmd도 코드페이지도 끼지 않는다. 긴 발행 작업에 막히지 않는다 |
| 2순위(백업) | 윈도우 작업 `V2R-Reconcile`, GPT 점검 작업 | 실행기가 아예 죽었을 때를 위한 안전망. 지우지 않는다 |
| 안전망 | 윈도우 작업 `V2R-Health` (`scripts/health-check.cmd`, 5분마다) | 심장박동이 3분 넘게 없으면 `V2R-Serve` 를 다시 켠다 |

실행기는 `scripts/serve.cmd` 로 24시간 돌고, 죽으면 30초 뒤 스스로 다시 켜진다.

### 관련 파일

| 파일 | 뜻 |
|---|---|
| `config/schedule.yaml` | 예약표(이름·시각·요일·명령) |
| `config/monitor.yaml` | 감시 설정(모델 진단 on/off, 하루 상한, 요약 시각, 캐시) |
| `v2r/engine/schedule.py` | 예약 발사 + 예약 감시견 + 심장박동 |
| `v2r/engine/monitor.py` | **모든 작업** 감시견 (Tier 0/1/2) |
| `v2r/engine/recovery_rules.py` | 오류 문구 → 복구 규칙 표 (토큰 0) |
| `v2r/engine/lock.py` | **단일 실행기 잠금** (`data/serve.lock`) |
| `data/schedule_state.json` | 예약별 마지막 발사일 + 확인 대기 목록 |
| `data/monitor_state.json` | 작업별 알림 여부·재시도 횟수·재시도 사슬·실행기 시작 시각·하루 집계 |
| `v2r/engine/sidecar.py` | **사이드카 스레드** (예약·감시·채널 수신·가벼운 작업, §3-3) |
| `data/serve_heartbeat.json` | 실행기 심장박동(매 틱 기록) |
| `data/sidecar_heartbeat.json` | 사이드카 심장박동(매 틱 기록, 3분 넘으면 경고) |
| `data/serve.lock` | 실행기 단일 실행 잠금(안에 프로세스 번호) |

## 2. 예약 흐름

예약·감시·채널 수신은 **사이드카 스레드**가 5초마다 돈다(§3-3). 긴 작업이 본 루프를
막고 있어도 그대로 돈다.

1. **예약 감시견** — 조금 전에 쏜 예약이 정말 큐에서 움직였는지 본다(5분).
2. **발사** — `due_entries(now, last_fired)` 가 고른 예약을 `worker.handle_text` 로 접수.
3. **작업 감시견** — 큐의 모든 작업을 점검(§3).
4. **심장박동** — `data/serve_heartbeat.json` 에 시각을 적는다.

규칙

- **두 번 쏘지 않는다** — `last_fired[이름] == 오늘` 이면 건너뛴다. 상태가 파일에 있으므로
  실행기를 껐다 켜도 같다.
- **놓친 예약은 따라잡는다** — 실행기가 꺼져 있었으면 켜지자마자 쏜다.
  기본 창은 **그날 23:59까지**. 좁히려면 `catch_up_minutes` 를 적는다.
- **중지에 막히지 않는다** — 예약을 쏘기 직전에 오래된 `data/STOP` 플래그를 지운다.

### 예약 감시견 (발사 후 5분)

| 시점 | 행동 |
|---|---|
| 5분 안에 작업이 `running`/`done` | 조용히 끝 |
| 5분이 지나도 `queued`거나 작업이 없음 | `예약 실패: <이름> — 자동 재시도` 알림 + **한 번** 재발사 |
| 그 뒤로도 5분 더 움직이지 않음 | 이유를 붙여 알림 + `error` 이벤트 기록 (사람 차례) |

## 3. 모든 작업 감시

사용자 규칙: **"모든 명령에 감시 에이전트 붙여."** 예약만이 아니라 큐에 들어온
모든 작업을 `v2r/engine/monitor.py` 가 매 틱 지켜본다.

| 상태 | 기준 | 자동 복구 |
|---|---|---|
| `queued` → 시작 안 함 | 5분 | `작업 N 시작 지연` 알림 + STOP 플래그 해제 + 만료된 실행기 리스 반납 |
| 그래도 시작 안 함 | 10분 | 이유(리스를 누가 잡고 있는지 등)를 붙여 다시 알림 |
| `running` 인데 기척 없음 | 15분 | `작업 N 정체 15분` 알림 |
| `running` 인데 30분 멈춤 + 리스 만료 | 30분 | 실패로 정리 → **같은 명령을 한 번** 다시 등록 |
| `failed` | 즉시 | 한 번만 알림 + 규칙에 따라 재시도/토큰 갱신/사람 (**§3-1 제외 규칙이 먼저**) |

"기척"은 `jobs.updated_at` 또는 그 작업의 마지막 이벤트다. 발행은 같은 카페의 글 사이에 2~5분씩
쉬고 요청 제한에 걸리면 더 오래 기다리므로, `_sleep_with_beat` 와 `_wait_for_rate_limit`
가 **10분마다 진행 이벤트**를 남긴다(`PROGRESS_EVENT_S`). 그래서 정상 대기를 정체로
오해하지 않는다.

같은 알림을 되풀이하지 않도록 알림 여부와 재시도 횟수는 `data/monitor_state.json`
에 남는다(재시작해도 유지).

### 3-1. 감시 제외 규칙 (장애 2026-09-20 A)

그날 아침, 새 감시견이 켜지자마자 **어제 일**을 건드렸다.

- 어제 실패한 작업 59·62를 새 일처럼 알렸다.
- 어제 실패한 작업 60(다시 해볼 수 없는 줄 2건)을 67로 다시 등록했다.
- 사용자가 `중지` 로 끊어 놓은 67을 또 70으로 다시 등록했다.

그래서 아래 네 가지를 **절대 하지 않는다**.

| 규칙 | 뜻 | 어디 |
|---|---|---|
| **과거는 건드리지 않는다** | 실행기가 켜진 시각(`started_at`, 프로세스마다 첫 틱에 정해 상태 파일에 기록)보다 **10분 넘게 전**에 멈춘 작업은 알리지도, 다시 등록하지도 않는다 | `monitor.started_at` / `monitor.is_history` (`HISTORY_GRACE_S = 600`) |
| **중지·취소는 실패가 아니다** | 오류 문구가 `중지·취소·cancel·리스 상실·lease` 에 걸리거나 상태가 `cancelled` 면 다시 등록하지 않는다 | `monitor.NO_RETRY_RE`, `no_retry_reason` |
| **재등록본은 또 재등록하지 않는다** | 멱등 키에 `\|monitor-retry` 가 들어 있으면 이미 감시가 한 번 다시 등록한 작업이다. 원래 작업 하나당 재등록은 **사슬 전체에서 1회**(`retry_chain`) | `monitor.root_key`, `may_retry` |
| **부분 성공은 보고만 한다** | `publish_*` 결과에 성공한 줄이 하나라도 있으면(`results` 또는 `per_cafe.ok`) 다시 올리지 않는다 — 다시 돌리면 중복 발행이 된다 | `monitor._success_rows` |

막힌 경우 알림에 이유가 그대로 붙는다: `다시 등록하지 않았습니다: 일부는 성공했습니다(성공 3건) — 다시 올리면 중복이 됩니다`.

### 3-2. 단일 실행기 잠금 (장애 2026-09-20 B)

같은 날 `publish_daily` 65와 67이 **나란히** 돌았다. 리스 소유자 이름이 호스트 이름뿐이라
같은 PC의 두 번째 실행기가 그 리스를 자기 것으로 봤기 때문이다. 세 겹으로 막는다.

1. **리스 소유자에 프로세스 번호** — `worker.default_owner()` 가 `호스트이름:pid` 를 준다.
   `JobStore.acquire` 는 살아 있는 **다른** 소유자가 잡은 리스를 절대 가져가지 않는다.
   앞 프로세스가 죽었으면(같은 호스트 + pid 가 죽음) 이어받는다 — 재시작이 막히지 않게.
2. **`data/serve.lock` 배타 잠금** — `serve()` 는 시작할 때 `worker.ensure_single_serve(rt)`
   로 이 파일을 잠근다(윈도우 `msvcrt.locking`, 그 밖 `fcntl.flock`). 못 잡으면 두 번째
   실행기이므로 **바로 끝낸다**: `이미 다른 실행기가 돌고 있습니다(프로세스 N번). ...`
   를 화면에 찍고 `serve 중복 실행 차단` 을 이벤트로 남긴다. 파일 앞부분에 pid 가 적혀 있다.
3. **발행 직전 한 겹 더** — `publish_daily 카페별` 작업은 시작 전에
   `worker.wait_for_other_publish` 로 다른 실행기가 발행 중인지 본다. 살아 있는 리스를 가진
   남의 `publish_*` 가 돌고 있으면 **기다린다**(30초마다 확인, 그동안 내 리스는 연장).
   2시간이 지나도 안 끝나면 경고 이벤트만 남기고 진행한다(영영 멈추지 않게).

> 프로세스 수로 세지 말 것 — venv 의 `python.exe` 는 자식 파이썬을 띄우는 껍데기라
> 실행기 1대당 파이썬이 2개로 보인다. 세는 기준은 **잠금 파일**이다.

`python -m v2r health` 첫머리에 누가 잡고 있는지 나온다.

```
실행기 심장박동: 4초 전 — 정상
단일 실행기 잠금: 프로세스 12345 번이 잡고 있습니다
```

### 3-3. 사이드카 스레드 (장애 2026-09-20 밤 → 09-21 아침)

10:50 에 시작한 `publish_daily` 가 다음 날 아침까지 돌았다. 그 사이 **본 루프가 통째로
막혀서** 이런 일이 벌어졌다.

- 11:00·14:00·17:00·21:00 `미처리 알림` 이 **한 번도 발사되지 않았다**
  (`schedule_state` 에 확인 대기 1건만 남아 있었다).
- 감시 틱이 안 돌아 멈춘 작업을 아무도 보지 못했다.
- **텔레그램 수신도 본 루프 안**에 있어서 `현황`·`중지` 가 읽히지도 않았다.
- 다음 날 07:30·09:00 예약은 긴 작업 뒤에 줄만 섰을 것이다.

원인은 하나다: `serve()` 가 큐에서 꺼낸 작업을 **그 자리에서** 실행한다.
그래서 긴 작업과 상관없이 돌아야 하는 일들을 **별도 스레드**로 옮겼다
(`v2r/engine/sidecar.py::SidecarThread`, 데몬, 5초 간격, 자기만의 `Runtime`·SQLite 연결).

| 누가 | 하는 일 |
|---|---|
| **사이드카 스레드** | 예약 틱 · 감시 틱 · **채널 수신**(명령 접수·답장) · **가벼운 작업 실행** · 사이드카 심장박동 |
| **본 루프(`serve`)** | 무거운 작업 실행(발행·세탁·정리 등) · 세션 점검 · 실행기 심장박동 · 사이드카 되살리기 |

- **가벼운 작업**(`sidecar.LIGHT_TASKS`, 한곳에서만 정한다): `pending_report`,
  `monitor_status`, `schedule_list`, `schedule_run`, `status`, `dashboard`, `gpt_keepalive`.
- 줄 나누기는 DB 칸 `jobs.lease_scope` (`light` / `main`) 로 한다. 등록할 때 작업 이름을 보고
  붙는다(`JobStore.enqueue`). 예전 DB 는 `store.db.migrate` 가 칸을 채운다.
  - 본 실행기는 `acquire(..., scope="main")` — **가벼운 작업을 집지 않는다.**
  - 사이드카는 `acquire_light()` — 무거운 작업을 절대 집지 않고, **실행기 리스를 쓰지 않는다.**
    그래서 긴 발행이 리스를 쥐고 있어도 `현황` 이 즉시 실행된다.
  - `python -m v2r "..."` 같은 한 번짜리 실행은 예전처럼 줄을 가리지 않는다(`scope=None`).
- SQLite 는 WAL 이라 두 연결이 같이 읽고 쓴다. 사이드카가 하는 쓰기는 모두 짧다.
- **`중지`** 는 사이드카가 읽어 `data/STOP` 플래그를 쓰고 열린 작업을 취소한다. 본 루프는
  슬롯 사이에서 `stop_requested(rt)`(파일)를 보므로 **긴 발행 중에도 바로 멈춘다.**
- 명령을 보낸 방에 답하는 정보(`worker.ORIGINS`)는 프로세스 한 곳에 모아 둔다 — 접수는
  사이드카, 실행은 본 루프여도 결과가 그 방으로 돌아간다.
- **되살리기**: 본 루프가 매 틱 `worker.ensure_sidecar` 로 스레드를 확인하고, 죽었으면
  `error` 이벤트 + 알림을 남기고 새로 띄운다.
- **심장박동 두 개**: `data/serve_heartbeat.json`(본 루프) / `data/sidecar_heartbeat.json`(사이드카).
  사이드카 쪽이 **3분** 넘게 낡으면 본 루프가 경고한다(`sidecar.alert_if_stale`, 10분에 한 번).
  `python -m v2r health` 에 두 줄이 함께 나온다.

```
실행기 심장박동: 4초 전 — 정상
사이드카 심장박동: 2초 전 — 정상
단일 실행기 잠금: 프로세스 12345 번이 잡고 있습니다
```

## 4. 비용 계단 (토큰을 태우지 않는다)

사용자 규칙: **감시는 기본적으로 AI 토큰을 쓰지 않는다.**

### Tier 0 — 기본, 토큰 0

순수 코드 점검만 한다. SQLite의 `jobs`·`events`, 심장박동 파일, 실행기 리스,
STOP 플래그, 세션 만료(`AuthSession.report()`). 복구도 규칙 기반이다:
STOP 해제, 만료 리스 반납, 한 번 재등록, 토큰 갱신, 실행기 재시작 안내.

오류 문구는 `v2r/engine/recovery_rules.py` 표로 맞힌다.

| 규칙 | 조치 | 뜻 |
|---|---|---|
| `rate_limited` | wait | 서버가 잠시 막음. 실행기가 기다린다 |
| `login_budget` | human | 하루 20회 로그인 한도 |
| `token_expired` | refresh | 토큰을 새로 받는다 |
| `network` | retry | 잠깐 끊김. 한 번 다시 |
| `catalog_mismatch` | human | 카페·게시판 이름이 사이트와 다름 |
| `photo_shortage` | human | 쓸 사진 부족 |
| `emoji` | human | 이모지 때문에 막힘 |
| `duplicate` | wait | 이미 올린 글(정상) |
| `lease_lost` | retry | 다른 실행기가 가져감 |

틱은 가볍게 유지한다(목표 50ms 미만). 같은 조회는 `cache_seconds`(기본 30초) 동안
다시 하지 않는다.

### Tier 1 — 선택, 상한 있음

**표에 없는 오류 문구일 때만** Haiku를 부른다.

- 같은 **오류 지문**(숫자를 지운 문구의 해시)당 **하루 한 번**.
- 하루 상한 `config/monitor.yaml: llm_diagnosis.daily_cap` (기본 20회).
- 하는 일은 딱 하나 — 기존 규칙 이름 중 하나로 **분류**하고 한국어 한 줄 설명을 준다.
- **절대 반복 호출하지 않는다.** 실패하면 그냥 Tier 2로 간다.
- 사용량은 `data/monitor_state.json` 의 그날 칸(`llm_calls`, `llm_tokens`)에 쌓이고
  텔레그램 `감시 상태` 에 그대로 보인다.

끄려면 `config/monitor.yaml` 에서 `llm_diagnosis.enabled: false`.

### Tier 2 — 사람

텔레그램 알림에 **규칙 이름 / 시도한 조치 / 그대로 복사해 보낼 재개 명령**을 넣는다.


`broadcast_document`, 채널 공통 진입점은 `channels.notify_document_all`.

## 7. 건강 점검 (실행기가 죽었을 때)

```
python -m v2r health
```

심장박동 나이(**실행기 + 사이드카 두 줄**, §3-3), **단일 실행기 잠금(잡고 있는 프로세스 번호)**,
예약 목록(다음/마지막 실행), 세션 상태를 한 번에 보여 준다.

`scripts/health-check.cmd` 는 이 보고를 `logs/health.log` 에 남기고,
심장박동이 **3분**보다 오래됐으면 `schtasks /run /tn V2R-Serve` 로 실행기를 다시 켠다.

5분마다 도는 윈도우 작업으로 등록(관리자 명령 프롬프트, 한 번만):

```
schtasks /create /tn "V2R-Health" /tr "\"D:\v2r 자동화\v2r-command-system\scripts\health-check.cmd\"" /sc minute /mo 5 /f
```

## 8. 장애 시 자동 복구 흐름 (한눈에)

```
09:00  예약 발사 ────► 큐 등록 ────► 실행 ────► 완료
         │                │            │
         │ 5분 안 움직임   │ 5분 대기    │ 15분 기척 없음
         ▼                ▼            ▼
   "예약 실패 — 자동 재시도"   "시작 지연"    "정체 15분"
   (1회 재발사)          + STOP 해제    30분 + 리스 만료
                        + 리스 반납     → 실패 정리 + 1회 재등록
         │                │            │
         └────────── 그래도 안 되면 ─────┘
                          ▼
              Tier 2: 사람에게 알림
        (규칙 이름 + 시도한 조치 + 재개 명령)
```

실행기 자체가 죽으면 → 심장박동이 멈춤 → `V2R-Health`(5분) 가 `V2R-Serve` 재시작
→ 켜지자마자 그날 놓친 예약을 따라잡는다.
